# Admin Bot — Telegram-бот для управления Piscine

Бот для администраторов школы программирования [Tomorrow School](https://tomorrow-school.com). Автоматически отправляет анонсы по расписанию — в чаты админов и подписчикам по выбранным ими бассейнам. Обновляет Google Sheets таблицы защит по команде или по нажатию кнопки.

## Что делает бот

Бот обслуживает шесть параллельных Piscine (все по 4 недели, включая неделю финального экзамена):

- **Piscine Go** и **Piscine JS** — с хакатоном на 3-й неделе;
- **Piscine AI 1 / AI 2 / AI 3** — три независимых параллельных потока одной AI-программы (различаются `parent.id`);
- **Piscine RUST** — без захардкоженных имён рейдов (generic-логика, номер недели по порядку рейдов).

Каждую неделю бот автоматически определяет текущую неделю через 01-edu API и отправляет нужные сообщения:

| День | Время | Сообщение | Недели |
|------|-------|-----------|--------|
| Пн | 10:00 | FAQ для новичков | только 1-я |
| Чт | 14:30 | Анонс экзамена + регистрация на рейд | 1–3 (не финальная) |
| Чт | 14:00 | Анонс Final Exam | только финальная |
| Пт | 10:00 | Анонс хакатона (Go и JS) | только 3-я |
| Вс | 15:00 | Напоминание о таблице защит + сообщение студентам | 1–3 (не финальная) |

Воскресное сообщение для админов содержит inline-кнопки для создания Google Sheets таблицы защит. Оно не приходит, пока рейд ещё не начался (идёт регистрация) — команд для расписания в этот момент нет.

Анонсы из таблицы (FAQ, экзамен, Final Exam, хакатон) уходят и в чаты `CHAT_IDS`, и — по выбранным бассейнам — тем, кто включил анонсы через `/subscribe`. Воскресное напоминание админам подписчикам не рассылается: это рабочее сообщение с кнопками, а не анонс.

| `ADMIN_CHAT_IDS` | нет | Allowlist групповых чатов, где одобренные пользователи могут выполнять команды (по умолчанию = `CHAT_IDS`) |
| `TIMEZONE` | нет | Часовой пояс для cron и расчёта дат (по умолчанию `Asia/Almaty`) |
| `TEMPLATES_PATH` | нет | Путь к шаблонам (по умолчанию `messages`) |
| `GOOGLE_CREDENTIALS_FILE` | нет | Путь к JSON-ключу сервисного аккаунта Google (для локального запуска / монтирования файла) |
| `GOOGLE_CREDENTIALS_JSON` | нет | Инлайн-содержимое JSON-ключа Google (для платформ без монтирования файлов, напр. Railway). Записывается во временный файл на старте |
| `SHEET_GO_WEEK{1..3}`, `SHEET_JS_WEEK{1..3}`, `SHEET_AI{1..3}_WEEK{1..4}` | нет | URL Google-таблиц защит по пискине и неделе |
| `SHEET_UNIVERSAL` | нет | Общая fallback-таблица защит для пискин без своей (Piscine RUST и динамически найденные пулы) |

> **Одна таблица — один слот.** Бот не создаёт таблицы (нет Drive API), он перезаписывает уже готовые: очищает рабочий диапазон и пишет расписание заново. Поэтому две переменные `SHEET_*` с одной и той же ссылкой — это потеря данных: таблица защит одной недели затирает другую. На старте бот логирует такие дубли (`several SHEET_* variables point at the same spreadsheet`), а `/create_tables` предупреждает об этом при записи. Если два бассейна с идущим рейдом указывают на один документ, команда не пишет ни один из них и предлагает обновить их по одному.
| `REGION_<NAME>_{CHECKIN,PISCINE,MODULE}_EVENT_ID` | нет | Пины авторитетных event ID по региону для `/get_region_updates` (см. заметку ниже) |

> **Регион-события.** Источник истины для `/get_region_updates` — это event ID, а не имя/порядок события. Любая метрика без пина откатывается на дефолтный поиск по path, так что пустые значения сохраняют прежнее поведение. Формат: `REGION_ASTANAHUB_CHECKIN_EVENT_ID=12345` (имя региона — регистронезависимо).

> **Путь чек-ина не одинаков во всех кампусах.** У Павлодара регистрация лежит на `/pavlodar/onboarding/check-in`, у всех остальных — на `/<кампус>/onboarding/checkin`. Точное сравнение по path показывало для Павлодара 0 вместо реальных 33, поэтому чек-ин ищется якорной регуляркой `^/<кампус>/onboarding/check-?in$` (`checkinPathPattern`). `games` и `module` во всех кампусах пишутся одинаково — они остались точным сравнением. Помните также, что чек-ин считается с фильтром `endAt > now`: после закрытия окна регистрации метрика законно становится 0.

> **`GOOGLE_FOLDER_ID`.** Присутствует в `.env.example`, но **сейчас не читается кодом** — это неиспользуемая переменная (кандидат на удаление или на доработку логики размещения таблиц в конкретной папке Drive).

### Настройка Google Sheets (опционально)

1. Создайте проект в [Google Cloud Console](https://console.cloud.google.com/)
2. Включите **Google Sheets API** и **Google Drive API**
3. Создайте **Service Account** → скачайте JSON-ключ
4. Дайте сервисному аккаунту доступ к нужным таблицам (Share → email сервисного аккаунта)
5. Подключите креды одним из двух способов:
   - **Локально / свой сервер:** положите JSON в корень (например `credentials.json`) и укажите `GOOGLE_CREDENTIALS_FILE=credentials.json`.
   - **Railway / платформы без файлов:** вставьте всё содержимое JSON в переменную `GOOGLE_CREDENTIALS_JSON` — на старте бот запишет его во временный файл и подхватит автоматически.

Без этой настройки бот работает, но кнопка «Создать таблицу» будет недоступна.

### Окно защиты: закончившийся рейд остаётся актуальным

Защита проходит **после** окончания рейда, поэтому закончившийся рейд не исчезает из бота в тот же день: он остаётся текущим до конца своей недели — до пятницы включительно (`usecase.DefenseWindowEnd`). Рейд, ивент которого закончился в понедельник 17.08, виден до 21.08.

- `/raid*` показывает такой рейд как «🏁 Рейд завершён — идёт защита» и называет дату, до которой информация актуальна, вместо «Активных рейдов нет»;
- `/week` помечает его как «завершён, идёт защита»;
- `/create_tables` строит для него таблицу защит (с предупреждением, что таблица перестроена заново и прежние записи очищены);
- как только окно закрывается, рейд перестаёт учитываться и команды отвечают как раньше.

### Когда таблицу защит создавать нельзя

Определение недели различает три состояния рейда (`domain.RaidStatus`): рейд ещё не начался (идёт регистрация), идёт сейчас, закончился. Таблицу защит можно строить только для идущего или недавно закончившегося рейда — в период регистрации команд ещё нет.

- `/create_tables` и кнопка «Обновить таблицу» в период регистрации отказываются работать и называют дату старта рейда;
- рейд без команд (`TeamsCount = 0`) тоже не пишется: пустая сетка затёрла бы содержимое документа. Нужна пустая таблица — `/edit_tables`;
- воскресное cron-напоминание о таблице защит до старта рейда не приходит;
- `/edit_tables` (ручной режим) **разрешает** подготовить таблицу заранее, но предупреждает, что рейд ещё не начался и число команд может измениться;
- бассейн, которого сейчас нет на платформе, помечается как «бассейн сейчас не идёт», а не как ошибка обновления таблицы.

### Анонсы и подписки

Анонсы адресуются не чатам, а пользователям: `/subscribe` даёт inline-экран, где каждый отмечает интересные ему бассейны и включает/отключает рассылку. Подписки лежат в JSON-сторе (`SUBSCRIPTION_STORE_PATH`).

- первый выбранный бассейн включает рассылку, снятие последнего — выключает; отдельный переключатель ставит рассылку на паузу, сохраняя выбор;
- пока рассылка включена, подписчику приходят cron-анонсы (FAQ, экзамен, финал, хакатон) по выбранным бассейнам. Рассылка в группы из `CHAT_IDS` работает как раньше;
- отправка идёт с паузой 50 мс между сообщениями (~20 msg/s), чтобы не упереться в лимит Telegram (~30 msg/s).

### `/announce` — готовый текст анонса

`/announce` **ничего не рассылает**: он отвечает готовым текстом, который админ копирует куда нужно. Диалог — максимум два нажатия и никакого состояния:

1. **бассейн** — шесть кнопок;
2. **тип анонса** — только у Piscine Go; у остальных бассейнов анонс один, и текст приходит сразу после выбора бассейна.

Набор анонсов задан в `domain.AnnouncementKindsFor()`:

| Анонс | Шаблон | Кому |
|---|---|---|
| 🎤 Запись на защиту | `student_message.txt` | всем бассейнам |
| ❓ Ответы на вопросы | `faq.txt` | только Piscine Go |
| 📢 Экзамен и рейд | `exam_announcement.txt` | только Piscine Go |
| 🚀 Хакатон | `hackathon.txt` | только Piscine Go |
| 🏁 Финальный экзамен | `final_exam.txt` | только Piscine Go |

- имя рейда подставляется автоматически: анонс о регистрации берёт идущий/ближайший рейд, анонс о защите — тот, который защищают (обычно уже закончившийся, см. окно защиты выше);
- ссылка на таблицу защит берётся по неделе рейда: у Go/JS/AI — только их собственная `SHEET_*` этой недели, у остальных — `SHEET_UNIVERSAL`. Если ссылки нет, бот пишет об этом строкой под текстом, а не подставляет чужую таблицу;
- бассейн едет в callback-данных кнопки, поэтому диалог не хранит состояние: кнопка, нажатая через час, всё ещё работает, а `/cancel` для анонсов больше не нужен;
- текст экранируется как HTML: анонсы — простой текст, зато сообщение с `<` или `&` гарантированно доставляется.

## Как работает определение недели

1. Запрос `GetCurrentPiscineId` — получает ID активного Piscine (по `startAt <= now() <= endAt`)
2. Запрос `GetRaidsByPiscine*Id` — получает все рейды этого Piscine
3. `findActiveRaid` — ищет активный рейд (где `startAt <= now <= endAt`)
4. Если активного нет, `findRecentlyEndedRaid` — недавно закончившийся рейд (до пятницы) попадает в `RecentRaid`
5. `findNextUpcomingRaid` — следующий рейд определяет неделю (идёт регистрация)
6. Если ни идущих, ни будущих рейдов нет — финальная неделя; её номер считается по фактическим рейдам (`finalWeekNumber`), а не по `TotalWeeks - 1`. Раньше бассейн с меньшим числом рейдов, чем в программе (у AI их два), не попадал ни в одну ветку и падал с ошибкой

По имени рейда определяется номер недели через маппинг в `domain.RaidWeekMap`:

| Piscine Go | Piscine JS | Piscine AI 1/2/3 |
|---|---|---|
| quad → неделя 1 | crossword → неделя 1 | backtesting-sp500 → неделя 1 |
| sudoku → неделя 2 | sortable → неделя 2 | forest-prediction → неделя 2 |
| quadchecker → неделя 3 | clonernews → неделя 3 | |
| (нет) → неделя 4 = Final | (нет) → неделя 4 = Final | |

Три потока Piscine AI используют одинаковую карту рейдов (одна программа, разные `parent.id`).
Piscine RUST не имеет захардкоженных имён рейдов: рейды берутся generic-запросом
`GetRaidsByParentId`, а номер недели вычисляется по порядку рейдов (`startAt` по возрастанию).

## Расчёт таблицы защит

### Автоматический режим (`/create_tables`, cron-напоминание)

`usecase.AutoScheduleParams` считает расписание **от дедлайна 17:30 назад** — защиты обязаны закончиться в 17:30, а стартуют настолько рано, насколько нужно по числу команд:

- **Строк** = ceil(N / 3), **колонок** = 3, **слот** = 30 минут;
- **Старт** = 17:30 − строк × 30 минут;
- **Перерывов нет** — сетка идёт подряд, чтобы арифметика «число команд → время старта» была однозначной.

Пример для 18 команд: 6 строк × 3 колонки = 18 слотов, окно 14:30–17:30 (последняя защита 17:00–17:30).

Расписание, которое не умещается в сутки, упирается в 00:00, а не уезжает в предыдущий день.

### Ручной режим (`/edit_tables`)

`usecase.CalculateDefenseScheduleWindow` заполняет заданное админом окно слотами выбранной длины; число строк определяется окном, а не числом команд (если мест меньше, чем команд, таблица всё равно создаётся — с предупреждением). Здесь работают перерывы:

- **Перерывы**: < 5 строк — нет; 5–10 — один (в середине); > 10 — два (на трети). Дополнительные перерывы вставляются, если иначе будет > 5 строк подряд без перерыва (`computeBreaks` / `enforceMaxConsecutive`).

### Перезапись таблицы

Перед записью бот сбрасывает и значения, **и** форматирование во всём рабочем диапазоне (`A1:Z1000`, обрезанном по фактической сетке листа), и возвращает колонкам ширину по умолчанию. Иначе после большой таблицы (10 строк с оранжевыми перерывами) на маленькой (3 строки без перерывов) оставались бы висеть старые заливки и границы. Если данные записались, а оформление применить не удалось, бот прямо пишет об этом в чат.

## Управление доступом

Авторизация построена на схеме «запрос → одобрение», а не на статическом списке чатов:

1. **Супер-админ** (`SUPER_ADMIN_USER_ID`) авторизован всегда и получает запросы доступа с inline-кнопками **Approve / Reject**.
2. Новый пользователь пишет боту и запрашивает доступ; запрос уходит супер-админу, который одобряет или отклоняет его кнопкой.
3. Одобренные пользователи сохраняются в JSON-стор (`ACCESS_STORE_PATH`, по умолчанию `data/access.json`) и работают в личке с ботом без доп. настройки; в групповых чатах команды разрешены только если чат есть в `ADMIN_CHAT_IDS` (по умолчанию `= CHAT_IDS`).
4. `ADMIN_USER_IDS` — заранее одобренный allowlist: при первом старте (пустой стор) эти ID добавляются как approved, чтобы существующий список админов продолжил работать. Идемпотентно: пользователи с уже существующей записью (в т.ч. отклонённые) не перезатираются.

Стор доступа и стор подписок на анонсы (`SUBSCRIPTION_STORE_PATH`, по умолчанию `data/subscriptions.json`) — единственное персистентное состояние бота. При деплое в контейнере их нужно хранить на volume (см. ниже), иначе при пересоздании контейнера теряются и одобренные через бота админы (вернутся только предодобренные `ADMIN_USER_IDS`), и подписки на анонсы.

## Деплой

Бот работает в режиме long-polling (только исходящий трафик), поэтому **не требует `EXPOSE` и открытых портов**.

### Docker Compose (локально / свой сервер)

```bash
docker compose up -d --build      # сборка + запуск в фоне
docker compose logs -f            # смотреть логи
docker compose down               # остановить и удалить контейнер
```

Конфигурация подхватывается из `.env` (тот же файл, что читает бинарник локально). Секреты не попадают в образ: `.dockerignore` держит `.env*` вне build-контекста, compose монтирует их только на рантайме через `env_file`. Одобренные админы (`data/access.json`) и подписки на анонсы (`data/subscriptions.json`) переживают пересоздание контейнера благодаря именованному volume `access-data:/app/data`.

### Railway

1. Заведите переменные из `.env.example` один в один в **Variables**: обязательные `TELEGRAM_TOKEN`, `ONEEDU_BASE_URL`, `PLATFORM_ACCESS_TOKEN`, `CHAT_IDS`, `SUPER_ADMIN_USER_ID` плюс нужные опциональные (`TIMEZONE`, `ADMIN_USER_IDS`, `SHEET_*`, `REGION_*_EVENT_ID`, …).
2. Google-креды передавайте **инлайном** через `GOOGLE_CREDENTIALS_JSON` (вставьте всё содержимое JSON-ключа) — Railway не монтирует файлы, поэтому `GOOGLE_CREDENTIALS_FILE` там не подходит. На старте бот запишет JSON во временный файл и подхватит его.
3. `ACCESS_STORE_PATH` (`data/access.json`) и `SUBSCRIPTION_STORE_PATH` (`data/subscriptions.json`) по умолчанию лежат рядом; для персистентности одобренных админов и подписок на анонсы между деплоями примонтируйте volume к `/app/data` (иначе сторы сбрасываются на каждом деплое).
